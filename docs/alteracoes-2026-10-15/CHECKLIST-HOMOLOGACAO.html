Checklist — Homologação do Sisaudin (JAR unificado)

Levantar o ambiente de homologação com o front e a API servidos pelo mesmo JAR. Referência: docs/alteracoes-2026-10-15/RELATORIO-ALTERACOES.md.

0 de 0

1. Servidor de homologação

Máquina separada da produção, ou a mesma com porta e banco próprios.

Java 17 ou mais novo instalado
java -version
MySQL acessível a partir do servidor

Pode ser o mesmo MySQL da produção, desde que com banco e usuário próprios (seção 3).

Porta 8081 livre e liberada no firewall para a rede interna
netstat -ano | findstr :8081

Sem resultado = porta livre.

SMTP falso instalado e rodando na porta 1025 obrigatório

MailHog ou smtp4dev. Captura os e-mails sem enviá-los.

O banco de homologação é uma cópia da produção, com os e-mails reais dos usuários. Sem o SMTP falso, a homologação envia e-mail de verdade.

Pasta de execução criada
New-Item -ItemType Directory C:\sisaudin-homolog

2. Backup da produção

Exportar o banco de produção no MySQL Workbench

Server > Data Export → selecionar o schema → Dump Structure and Data → Export to Self-Contained File.

Marcar: Create Dump in a Single Transaction, Dump Stored Procedures, Events, Triggers.

Deixar Include Create Schema desmarcado. Com ele, a importação recria o schema com o nome de produção e pode sobrescrevê-lo.

Copiar a pasta uploads\ da produção opcional

Necessária para abrir os anexos já existentes. Fica na pasta de onde o backend de produção é executado.

Guardar o arquivo .sql em local de acesso restrito

O dump contém dados reais. Anotar o nome do arquivo no topo deste checklist.

3. Banco de homologação

Criar o banco e o usuário próprio

No Workbench, conectado como administrador. Trocar a senha.

CREATE DATABASE sisaudin_homolog CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'sisaudin_hml'@'localhost' IDENTIFIED BY 'TROCAR_SENHA_BANCO';
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX, REFERENCES, DROP
  ON sisaudin_homolog.* TO 'sisaudin_hml'@'localhost';

MySQL em outra máquina: trocar 'localhost' pelo IP do servidor de homologação.

Restaurar o backup no banco novo

Server > Data Import → Import from Self-Contained File → Default Target Schema = sisaudin_homolog → Start Import.

Conferir que a restauração foi para o banco certo
SELECT table_schema, COUNT(*) AS tabelas
FROM information_schema.tables
WHERE table_schema IN ('sisaudin_homolog')
GROUP BY table_schema;

SELECT COUNT(*) FROM sisaudin_homolog.item_trabalho;
Conferir que o banco restaurado é mesmo a produção e tem a estrutura do sistema atual crítico
SELECT table_name, engine, table_rows, create_time
FROM information_schema.tables
WHERE table_schema = 'sisaudin_homolog'
  AND table_name IN ('item_trabalho', 'relatorio_preliminar', 'pessoa', 'doc_relatorio')
ORDER BY table_name;

Esperado: item_trabalho e relatorio_preliminar existem, com linhas, e create_time de hoje (hora da importação).

Sem item_trabalho (só doc_relatorio, doc_os, item): é a estrutura antiga do sistema. O JAR criaria tabelas novas e vazias e o sistema abriria sem dados. Não subir; a implantação exige migração de dados.
create_time antigo: o banco não é o que acabou de ser restaurado (importação foi para outro nome).

Conferir o mecanismo das tabelas (MyISAM × InnoDB)
SELECT engine, COUNT(*) AS tabelas
FROM information_schema.tables
WHERE table_schema = 'sisaudin_homolog' AND table_type = 'BASE TABLE'
GROUP BY engine;

Esperado: só InnoDB. Tabelas MyISAM não têm transação nem chave estrangeira, e o ddl-auto=update falha nelas com Specified key was too long; max key length is 1000 bytes. Se houver MyISAM, converter na homologação (gerar os comandos com a consulta abaixo, rodar com a aplicação parada) e registrar para fazer o mesmo na produção:

SELECT CONCAT('ALTER TABLE `', table_name, '` ENGINE=InnoDB;')
FROM information_schema.tables
WHERE table_schema = 'sisaudin_homolog' AND engine = 'MyISAM';
Verificar se o banco já tem a coluna especial
SELECT table_name, column_name
FROM information_schema.columns
WHERE table_schema = 'sisaudin_homolog' AND column_name = 'especial';

Sem resultado = produção ainda sem a entrega de 08/10 (RAI/REAI). É o esperado: a coluna será criada e preenchida na subida do JAR (seção 7). Siga as consultas abaixo.

Com resultado = a coluna já existe; a prévia abaixo continua útil, mas a migração só vai preencher os registros com especial nulo.

Rodar as consultas de antes da subida e guardar o resultado

Não usam a coluna especial, então funcionam no banco recém-restaurado. Servem de base para a conferência da seção 9. Salvar o resultado (no Workbench: botão Export da grade de resultado).

USE sisaudin_homolog;

-- A. Prévia de como a migração vai classificar os relatórios existentes
--    (mesma regra da RelatorioEspecialMigration: "EXTRA" na sigla do item = REAI)
SELECT 'preliminar' AS tabela,
       IF(UPPER(COALESCE(i.sigla,'')) LIKE '%EXTRA%', 'REAI', 'RAI') AS tipo, COUNT(*) AS qtd
FROM relatorio_preliminar r LEFT JOIN item_trabalho i ON i.id = r.item_trabalho_id GROUP BY 2
UNION ALL
SELECT 'final', IF(UPPER(COALESCE(i.sigla,'')) LIKE '%EXTRA%', 'REAI', 'RAI'), COUNT(*)
FROM relatorio_final r LEFT JOIN item_trabalho i ON i.id = r.item_trabalho_id GROUP BY 2;

-- B. Número repetido no mesmo tipo e ano, pela classificação acima
SELECT IF(UPPER(COALESCE(i.sigla,'')) LIKE '%EXTRA%', 'REAI', 'RAI') AS tipo, r.ano, r.numero,
       COUNT(*) AS qtd, GROUP_CONCAT(r.id) AS ids
FROM relatorio_preliminar r LEFT JOIN item_trabalho i ON i.id = r.item_trabalho_id
WHERE r.numero IS NOT NULL GROUP BY 1, 2, 3 HAVING COUNT(*) > 1;

-- C. Item com mais de um relatório preliminar
SELECT item_trabalho_id, COUNT(*) AS qtd, GROUP_CONCAT(id) AS ids
FROM relatorio_preliminar WHERE item_trabalho_id IS NOT NULL
GROUP BY item_trabalho_id HAVING COUNT(*) > 1;

-- D. Relatórios sem item de trabalho
SELECT 'preliminar' AS tabela, id, ano, numero FROM relatorio_preliminar WHERE item_trabalho_id IS NULL
UNION ALL
SELECT 'final', id, ano, numero FROM relatorio_final WHERE item_trabalho_id IS NULL;

-- E. Itens que não podem gerar relatório novo (sem tipo PAINT/EXTRA)
SELECT i.id, i.sigla, t.nome AS tipo
FROM item_trabalho i LEFT JOIN tipo_item t ON t.id = i.tipo_item_id
WHERE t.nome IS NULL
   OR (UPPER(t.nome) NOT LIKE '%EXTRA%' AND UPPER(t.nome) NOT LIKE '%PAINT%');

-- F. Relatórios de item EXTRA (pelo cadastro) que a migração vai marcar como RAI,
--    porque a sigla do item não contém "EXTRA"
SELECT 'preliminar' AS tabela, r.id, i.sigla, t.nome AS tipo_item, r.ano, r.numero
FROM relatorio_preliminar r
JOIN item_trabalho i ON i.id = r.item_trabalho_id
JOIN tipo_item t ON t.id = i.tipo_item_id
WHERE UPPER(t.nome) LIKE '%EXTRA%' AND UPPER(i.sigla) NOT LIKE '%EXTRA%'
UNION ALL
SELECT 'final', r.id, i.sigla, t.nome, r.ano, r.numero
FROM relatorio_final r
JOIN item_trabalho i ON i.id = r.item_trabalho_id
JOIN tipo_item t ON t.id = i.tipo_item_id
WHERE UPPER(t.nome) LIKE '%EXTRA%' AND UPPER(i.sigla) NOT LIKE '%EXTRA%';

A consulta F mostra os relatórios antigos que ficarão como RAI em item EXTRA. Eles continuam funcionando; reclassificar é decisão caso a caso (pode gerar número repetido na sequência REAI). Anotar a quantidade nas observações.

4. Gerar o JAR (máquina de desenvolvimento)

Parar o backend local

O build escreve em backend/target.

Gerar o front no modo unificado
cd frontend
npx.cmd vite build --mode unificado

Não usar npm run build: ele aponta para a produção.

Usar npx.cmd, e não npx: no PowerShell, npx chama o npx.ps1, que a política de execução do Windows costuma bloquear ("a execução de scripts foi desabilitada neste sistema"). O mesmo vale para npm.cmd.

Conferir que o build não aponta para a produção
(Select-String -Path dist\assets\*.js -Pattern 'sisaudin.ghc.com.br' -SimpleMatch).Count

O resultado tem de ser 0.

Gerar o JAR
cd ..\backend
.\mvnw.cmd clean package -DskipTests

Sai backend\target\sisaudin-0.0.1-SNAPSHOT.jar (cerca de 250 MB).

Conferir que o front entrou no JAR
Add-Type -A System.IO.Compression.FileSystem
$z = [IO.Compression.ZipFile]::OpenRead((Resolve-Path target\sisaudin-0.0.1-SNAPSHOT.jar))
$z.Entries | Where-Object FullName -like 'BOOT-INF/classes/static/index.html' | Select-Object FullName
$z.Dispose()

Tem de listar BOOT-INF/classes/static/index.html. Sem ele, o JAR sobe sem telas.

Se o frontend/dist também alimenta o nginx de produção, refazer o build de produção antes de publicar lá

Rodar duas vezes e colar em jwt.access.secret e jwt.refresh.secret:

$b = New-Object byte[] 64; [Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b); [Convert]::ToBase64String($b)

7. Subir a aplicação

Iniciar o JAR de dentro da pasta de execução
cd C:\sisaudin-homolog
java -jar sisaudin-0.0.1-SNAPSHOT.jar

Executar de dentro da pasta: é dali que o Spring lê o application.properties externo e onde fica uploads\.

Primeira subida (banco sem a coluna especial): gravar a saída inteira do console, porque a mensagem da migração (próximo item) não vai para o arquivo de log:

cd C:\sisaudin-homolog
cmd /c "java -jar sisaudin-0.0.1-SNAPSHOT.jar > primeira-subida.txt 2>&1"

Acompanhar em outra janela:

Get-Content C:\sisaudin-homolog\primeira-subida.txt -Wait -Tail 50

Nas subidas seguintes, o log fica em logs\sisaudin.log (chave logging.file.name; sem ela, só no console):

Get-Content C:\sisaudin-homolog\logs\sisaudin.log -Wait -Tail 50
Log mostra Started SisaudinApplication e nenhum ERROR
Mensagem no logCausa provável
Access denied for userusuário, senha ou GRANT do MySQL (seção 3)
Unknown databasenome do banco na spring.datasource.url
WeakKeyException / Illegal base64segredo JWT colado incompleto
Port 8081 was already in useoutro processo na porta (seção 1)
Log mostra a classificação dos relatórios antigos (coluna especial)

Na primeira subida sobre um banco sem a coluna, o Hibernate cria especial e a RelatorioEspecialMigration a preenche. Devem aparecer, uma vez cada:

[RelatorioEspecialMigration] RelatorioPreliminar: N marcados como REAI, M como RAI.
[RelatorioEspecialMigration] RelatorioFinal: N marcados como REAI, M como RAI.

N e M devem bater com a consulta A da seção 3. Nas subidas seguintes a mensagem não aparece mais (não há registro nulo para preencher).

A mensagem sai por System.out: aparece no console ou no primeira-subida.txt, nunca no logs\sisaudin.log. Se ela se perdeu, a conferência da seção 9 mostra o mesmo resultado no banco.

Sem a mensagem e com erro de ALTER no log: falta permissão ALTER ao usuário do banco (seção 3). Para criar a coluna à mão, como administrador, e subir de novo:
ALTER TABLE relatorio_preliminar ADD COLUMN especial BIT(1) NULL;
ALTER TABLE relatorio_final ADD COLUMN especial BIT(1) NULL;

Anotar as alterações de estrutura que o Hibernate fez na subida

Com ddl-auto=update, colunas e tabelas novas aparecem no log como alter table / create table (se show-sql estiver ligado) ou podem ser vistas comparando o schema com o da produção.

Registrar como serviço do Windows opcional

WinSW ou NSSM, com o diretório de trabalho em C:\sisaudin-homolog e o mesmo usuário da seção 6.

Nginx com HTTPS na frente opcional

Só como proxy de tudo para a porta 8081. Se usar, ajustar sisaudin.link para o endereço HTTPS.

client_max_body_size 50m;
location / {
    proxy_pass         http://127.0.0.1:8081;
    proxy_set_header   Host              $http_host;
    proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header   X-Forwarded-Proto $scheme;
    proxy_read_timeout 120s;
}

9. Conferência final

Coluna especial criada e preenchida em todos os relatórios
SELECT 'preliminar' AS tabela,
       CASE WHEN especial IS NULL THEN 'NULO' WHEN especial = 1 THEN 'REAI' ELSE 'RAI' END AS tipo,
       COUNT(*) AS qtd
FROM relatorio_preliminar GROUP BY 2
UNION ALL
SELECT 'final',
       CASE WHEN especial IS NULL THEN 'NULO' WHEN especial = 1 THEN 'REAI' ELSE 'RAI' END,
       COUNT(*)
FROM relatorio_final GROUP BY 2;

Os totais devem bater com a consulta A da seção 3 e não pode haver linha NULO.

Números repetidos agora pela coluna especial
SELECT 'preliminar' AS tabela, ano, especial + 0 AS reai, numero, COUNT(*) AS qtd, GROUP_CONCAT(id) AS ids
FROM relatorio_preliminar WHERE numero IS NOT NULL
GROUP BY ano, especial, numero HAVING COUNT(*) > 1
UNION ALL
SELECT 'final', ano, especial + 0, numero, COUNT(*), GROUP_CONCAT(id)
FROM relatorio_final WHERE numero IS NOT NULL
GROUP BY ano, especial, numero HAVING COUNT(*) > 1;

O resultado do preliminar deve ser igual ao da consulta B da seção 3. Os repetidos já existiam; os novos números saem do maior + 1 e não são afetados.

Rodar de novo as consultas C, D e E da seção 3 e comparar

Não pode aparecer inconsistência nova além dos relatórios de teste (já excluídos).

Relatórios fora da regra (tipo do relatório × tipo do item)
SELECT 'preliminar' AS tabela, r.id, r.item_trabalho_id, t.nome AS tipo_item,
       IF(COALESCE(r.especial,0) = 1, 'REAI', 'RAI') AS tipo_relatorio, r.ano, r.numero
FROM relatorio_preliminar r
JOIN item_trabalho i ON i.id = r.item_trabalho_id
LEFT JOIN tipo_item t ON t.id = i.tipo_item_id
WHERE COALESCE(r.especial,0) <> (UPPER(COALESCE(t.nome,'')) LIKE '%EXTRA%');

O resultado deve conter só relatórios antigos.
